# Termihomo 产品需求规格（PRODUCT_SPEC）

> 文档状态：产品基线\
> 项目定位：跨平台、纯终端的 Mihomo 代理管理应用  
> 主要语言：Go  
> 产品形态：TUI + CLI  
> 首发目标：Linux AMD64 / ARM64，随后扩展 macOS、Windows、Android Termux 与 Docker

## 1. 产品定位

Termihomo 是一款跨平台、纯终端的代理管理应用。它复用 Mihomo 作为代理内核，通过统一的 Go 应用提供内核生命周期管理、代理配置管理、实时监控、交互式终端界面和可脚本化 CLI。

交互体验参考 htop、btop、lazygit：信息密度高、布局清晰、键盘操作优先、必要时支持鼠标，不依赖桌面环境。

### 1.1 核心目标

1. 用户无需手动下载、安装和维护 Mihomo，即可通过 Termihomo 建立可用的代理环境。
2. 用户可以通过 TUI 查看和管理节点、策略组、订阅、规则、连接、流量、日志和配置。
3. TUI 退出后，受 Termihomo 管理的 Mihomo 可以继续在后台运行。
4. 同一套 Go 业务逻辑和尽可能一致的交互方式覆盖不同操作系统和运行环境。
5. 同一套业务服务同时支持交互式 TUI 和脚本化 CLI。
6. 尽量复用 Mihomo 已有能力，不重新实现代理协议、DNS、规则引擎和数据转发。

### 1.2 非目标

首版不做以下事情：

- 不自行实现代理协议或替代 Mihomo 内核。
- 不开发 GUI、Web 控制台或手机原生界面。
- 不承诺所有平台都能以相同权限实现 TUN / 系统级流量接管。
- 不在首版实现远程多设备管理、多实例编排或复杂 SSH 管理平台。
- 不内置订阅转换服务；优先兼容 Mihomo 原生配置及常见 Clash YAML 订阅输出。
- 不把 TUI 进程作为代理流量转发链路的一部分。

## 2. 目标用户与典型场景

### 2.1 目标用户

- 在 VPS、云服务器、NAS 上运行代理服务的用户。
- 使用 SSH 管理 Linux 服务器的用户。
- 希望在 macOS、Windows 终端中管理 Mihomo 的用户。
- 希望在 Android Termux 中直接使用终端代理管理工具的用户。
- 希望在 Docker 容器中运行和管理代理服务的用户。
- 熟悉 Clash 配置，但不希望依赖图形客户端的高级用户。

### 2.2 典型使用流程

1. 安装 Termihomo。
2. 首次运行时自动识别操作系统和 CPU 架构。
3. Termihomo 检查 Mihomo 是否已安装。
4. 由 Termihomo 安装并管理本机 Mihomo；连接非托管内核是后续能力。
5. 添加订阅或导入本地 YAML 配置。
6. 校验配置并启动内核。
7. 在 Dashboard 查看运行状态和实时流量。
8. 在 Proxies / Groups 页面测速、选择节点和切换策略组。
9. 查看实时日志；独立的连接、规则和配置编辑页面在后续版本提供。
10. 退出 TUI，Mihomo 按当前运行模式继续运行。

## 3. 三层核心产品架构

### 3.1 Core Manager（内核管理层）

负责 Mihomo 二进制文件和进程生命周期：

- 检测操作系统、CPU 架构和运行环境。
- 下载适配当前平台的 Mihomo 发行版本。
- 校验下载文件完整性。
- 安装、升级、切换和回滚内核版本。
- 启动、停止、重启 Mihomo。
- 检查进程状态和 API 健康状态。
- 获取运行时间、版本、启动参数和资源使用情况（可获取时）。
- 管理运行目录、配置路径、日志路径和控制器配置。
- 确保退出 TUI 不会意外停止后台 Mihomo。
- 区分“进程存活”和“控制 API 可用”，避免误报状态。

### 3.2 Proxy Manager（代理管理层）

负责 Mihomo 配置和代理能力的管理：

- Profiles：订阅与配置文件。
- Proxies：代理节点。
- Groups：代理策略组。
- Rules：规则和规则提供者。
- Connections：活动连接。
- Traffic：实时流量。
- Logs：内核日志。
- DNS：DNS 配置及可获得的诊断信息。
- Config：YAML 查看、编辑、校验、备份和重载。

### 3.3 Terminal Experience（终端体验层）

负责用户交互和自动化入口：

- TUI Dashboard。
- 页面导航和快捷键。
- 列表、搜索、筛选、排序和分页。
- 表单编辑、确认弹窗和 Diff。
- 实时数据展示。
- CLI 命令。
- JSON 输出、非交互模式和标准退出码。
- 终端尺寸、颜色能力和窄屏适配。

#### Proxies（代理节点）

- 展示代理节点名称、类型、延迟和可用状态（P0）。
- 展示当前选中节点（P0）。
- 搜索、过滤和排序（P0）。

- 批量延迟测试（P1）。
- 节点详情及所属策略组（P1）。
- 测速超时和测试 URL 设置（P1）。

#### Groups（策略组）

- 展示策略组及类型（P0）。
- 展示当前选项（P0）。
- 展示组内可选节点或子策略组（P0）。
- 切换 Selector 类策略组的选项（P0）。
- 展示 URL-Test、Fallback、Load-Balance 等组的状态（P1）。
- 搜索和过滤（P1）。
- 展示策略组关系和嵌套层级（P1）。

具体操作必须根据 Mihomo API 对不同策略组类型的支持情况实现，不得把所有组都当作可手动选择的 Selector。

#### Rules（规则）

- 查看规则及顺序（P1）。

- 通过配置编辑器修改规则（P1）。
- 保存前校验并提供 Diff（P1）。

规则列表 API 是否提供完整规则内容、运行时匹配详情等能力，应在技术调研阶段核实；不支持的能力不应伪装成已实现。

- 关闭全部连接（P1）。


CLI 要求：

- TUI 与 CLI 共用同一套应用服务和业务逻辑。
- 支持非交互执行。

## 5. 平台支持矩阵

平台支持分为“应用可运行”和“系统网络能力可用”两个维度。不能因为 Go 程序能编译，就宣称该平台的所有 Mihomo 功能均可用。

| 平台 | Termihomo TUI/CLI 目标 | Mihomo 内核目标 | 普通代理端口 | TUN / 系统接管 |
|---|---|---|---|---|
| Linux AMD64 | 首发 | 首发 | 支持 | 需权限和设备 |
| Linux ARM64 | 首发 | 首发 | 支持 | 需权限和设备 |
| macOS ARM64 | 后续 | 核实官方构建 | 支持 | 需系统权限 |
| macOS AMD64 | 后续 | 核实官方构建 | 支持 | 需系统权限 |
| Windows AMD64 | 后续 | 核实官方构建 | 支持 | 需相应权限/组件 |
| Windows ARM64 | 调研后支持 | 核实官方构建 | 视构建而定 | 视系统能力而定 |
| Android Termux ARM64 | 重点适配 | 使用 Android 对应构建并实测 | 目标支持 | VPNService / Root 等额外条件 |
| Docker Linux | 后续适配 | 取决于镜像架构 | 支持 | 需要设备和容器权限 |

### 平台适配要求

- 路径、权限、进程启动、信号、服务管理必须封装在平台适配层。
- Termux 不能直接等同于普通 Linux 发行版；需要实际验证 Android/Bionic 构建。
- Docker 首版优先采用容器内单实例模式，使用 Volume 持久化配置；TUN 需要额外容器权限。
- 普通 HTTP/SOCKS 代理端口模式应优先覆盖更多平台。
- TUN、系统代理设置和开机服务集成按平台分别实现，不强求完全相同。

## 6. 安全与数据要求

- Mihomo External Controller 默认只监听回环地址。
- 默认生成随机 API Secret，并以平台允许的最小权限保存。
- 禁止默认将无认证 Controller 暴露到公网。
- 远程控制功能在后续版本实现，要求 TLS/WSS 或安全隧道。
- 订阅 URL 可能包含凭据，必须按 Secret 处理。
- 日志和错误信息必须对订阅凭据、API Secret 等敏感值脱敏。
- 配置文件和备份文件设置合理权限。
- 对修改配置、关闭全部连接、停止内核等操作提供确认。
- 下载内核时校验来源、版本和摘要；发布物与许可证义务需要在发布前核实。
- 记录关键管理操作，但不得记录敏感凭据。

## 8. 验收标准

V0.1 必须通过以下端到端验收：

1. 在干净的 Linux AMD64 环境中安装 Termihomo。
2. 自动识别平台并下载、校验、安装 Mihomo。
3. 添加有效 Clash YAML 订阅并通过配置校验。
4. 启动 Mihomo，确认进程存活且 Controller API 可用。
5. 在 TUI 中看到节点和策略组。
6. 切换 Selector 策略组中的选项，并通过实际代理请求验证生效。
7. 能看到持续更新的流量数据。
8. 能查看内核日志。
9. 退出 TUI 后 Mihomo 仍运行。
10. 重新进入 TUI 能重新连接并显示正确状态。
11. 无效配置不得替换旧配置；重载失败时恢复旧文件和旧的运行配置，并以实际代理请求验证。
12. 内核进程退出时能准确识别并提示。
13. go test ./...、go vet ./... 和目标平台构建通过。
14. Controller 仅绑定本机回环地址，未认证请求无法访问管理接口。
15. 在 Linux ARM64 环境中实跑安装、启动、实际代理请求和退出后重连；交叉编译不能替代运行验收。
16. TUI 打开时，`status --json` 仍能独立返回可解析状态。

## 9. 产品原则

1. **复用成熟内核**：不重写 Mihomo 已有的网络能力。
2. **三层解耦**：Core Manager、Proxy Manager、Terminal Experience 有清晰边界。
