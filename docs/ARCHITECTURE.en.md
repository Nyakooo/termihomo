# Architecture

This document describes Termihomo's module boundaries, runtime model, and configuration flow. It is intended for readers who want to understand the implementation, troubleshoot issues, or contribute code.

## 1. Project scope

Termihomo is a terminal manager for Mihomo. It does not implement proxy protocols and does not replace the Mihomo core.

- **Mihomo** handles proxy protocols, rule matching, DNS forwarding, and network traffic.
- **Termihomo** manages core installation and lifecycle, profiles, proxies and policy groups, runtime state, and the TUI / CLI experience.

This boundary lets the project focus on management workflows while reusing Mihomo's existing capabilities.

## 2. Layers

```text
User
 ├─ TUI (interactive terminal interface)
 └─ CLI (commands and scripts)
          │
          ▼
     Core Manager
 ├─ Mihomo process lifecycle
 ├─ Profiles and configuration
 ├─ Controller API client
 ├─ Proxies, policy groups, connections
 ├─ DNS, rules, and logs
 └─ Network and system proxy settings
          │
          ├──────── Local config / data / logs
          │
          ▼
       Mihomo Core
       Proxy data plane
```

### Interaction layer

| Package | Responsibility |
| --- | --- |
| `cmd/termihomo` | Application entry point |
| `internal/cli` | Command dispatch, CLI operations, and TUI startup |
| `internal/tui` | Terminal layout, pages, input handling, and UI state |
| `internal/i18n` | Simplified Chinese and English strings |

The TUI and CLI use the same Core Manager rather than maintaining separate proxy-management implementations.

### Management layer

| Package | Responsibility |
| --- | --- |
| `internal/core` | Mihomo lifecycle, config generation and validation, Controller API, profiles, proxies, connections, DNS, rules, and network settings |
| `internal/update` | Termihomo self-update |
| `internal/version` | Build version information |

The Core Manager is the management boundary between the application and Mihomo. The TUI and CLI do not depend on Mihomo internals.

### Platform layer

`internal/platform` handles application directories, process locks, and platform-specific paths. OS-specific implementations are isolated with Go build tags, including system proxy, process management, and startup integration.

## 3. Runtime model

Termihomo manages Mihomo as a separate background process:

1. Install the core with <code>termihomo install</code> or the Install / reinstall action on the TUI Core page. The installation flow downloads and verifies a supported build.
2. Read the active profile and application overrides.
3. Generate a managed configuration and ask Mihomo to validate it.
4. Start Mihomo and use its local Controller API to inspect runtime state.
5. Let the TUI / CLI query traffic, proxies, policy groups, connections, DNS events, and logs as needed.

Closing the TUI does not stop Mihomo. The core runs independently and can be stopped explicitly with `termihomo stop`.

## 4. Configuration flow

Configuration has two sources:

- **Profiles**: a local Mihomo YAML file or a subscription URL.
- **Application settings**: settings changed through Termihomo and its override file.

When starting or reloading, Termihomo generates a managed configuration from the active profile and application settings, then validates it with Mihomo. The configuration is applied only after validation succeeds.

The generated runtime configuration is not the sole source of truth. It is an application-managed artifact and may be replaced during a later regeneration. See [Configuration and data](CONFIGURATION.en.md).

## 5. Platform differences

Linux, macOS, and Windows share most Go code, but system integration depends on OS capabilities and permissions:

- System proxy detection, updates, and restoration use platform-specific implementations.
- Startup integration uses the mechanism provided by each platform.
- TUN requires network privileges; exact requirements depend on the operating system and environment.
- Terminal size, mouse events, and terminal capabilities can affect the TUI.

A successful cross-platform build does not imply identical behavior for every system-network feature on every environment.

## 6. Security boundaries

- Application config, data, and log directories are created as private user-accessible directories.
- The default mixed-proxy listener is `127.0.0.1:7890`; LAN access is disabled by default.
- The Mihomo Controller uses a local address and credentials generated by the application.
- Enabling TUN or changing the system proxy changes system networking and should be done with care.
- Subscription URLs may contain credentials. Redact URLs and sensitive data before sharing logs or config files.

## 7. Code map

```text
cmd/termihomo/       Application entry point
internal/cli/        CLI commands
internal/tui/        TUI pages and interaction
internal/core/       Mihomo management and core logic
internal/platform/   Platform integration
internal/update/     Self-update
internal/i18n/       Localization
internal/version/    Version information
test/                Installer and release smoke tests
```

When adding a capability, prefer implementing it in the relevant Core Manager area and then exposing it through the TUI or CLI. Avoid scattering business logic across presentation code.
